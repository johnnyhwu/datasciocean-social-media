# SAG 第 2 則（SQL、向量、LLM 怎麼分工）hook 候選

第 1 則的樣態是「讀者疑問」，所以第 2 則不能再用讀者疑問（batch_check 會擋相鄰同樣態）。
封面渲染上限：主標 2 行。副標都要補「SAG 是什麼」，沒看過第 1 則的人才看得懂。

## A 並列重點（卡上原句「分工分得很死」）
- 主標：SQL、向量、LLM，[[分工]]分得很死
- 副標：SAG 這個 RAG 做法：SQL 連事件、向量補別名與錯字，LLM 只判斷縮到 100 個以內的候選。（論文：arxiv.org/abs/2606.15971）
- 沒看過系列的人：知道是三個東西分工的檢索做法。

## B 反直覺斷言（目前 spec 暫用）
- 主標：SAG 不靠[[更強的模型]]，靠[[分工]]
- 副標：這個 RAG 做法：SQL 串事件、向量補語意，LLM 只在候選縮到 100 個以內才出場。（論文：arxiv.org/abs/2606.15971）
- 沒看過系列的人：知道 SAG 是個靠分工而不是靠大模型的做法。

## C 情境痛點
- 主標：想讓 LLM [[少讀資料]]、少花錢？
- 副標：SAG 的做法：先用 SQL 和向量一路篩，LLM 只看最後縮到 100 個以內的候選。
- 沒看過系列的人：知道是省 LLM 用量的檢索做法。（「少花錢」對應卡上 c7「token 消耗與 API 成本壓得很低」）

## D 數字落差
- 主標：LLM 只看 [[100 個]]候選，成本壓得很低
- 副標：SAG：SQL 和向量先把候選篩到 100 個以內，LLM 才出場做聯合判斷。
- 沒看過系列的人：知道 LLM 只看很少量資料。

## E 口語反差
- 主標：把活分給 SQL 和向量，[[LLM]] 只在最後出手
- 副標：SAG 這個 RAG 做法：多步推理交給 SQL，LLM 只判斷縮到 100 個以內的候選。
- 注意：卡寫「多步推論」，貼文用語寫 Multi-Hop。

## F 代價式提問（避開讀者疑問樣態的陳述版）
- 主標：LLM 在檢索裡[[別做太多事]]
- 副標：SAG 的 RAG 做法：SQL 負責串、向量負責補，LLM 最後只從 100 個以內挑。
- 注意：「別做太多事」是建議語氣，比卡強（卡是描述設計），可能被忠實者擋。
